# The first milestone (M1)


> Part of the claude-domore design, 2026-09-26. Status: proposal, nothing built. The overview is [what-we-could-build.md](../what-we-could-build.md). The first end-to-end loop: its scope, the acceptance tests, and the milestones that come after it.

## Scope

From [CODEX]:
- **In scope:** one approved repository; one queued task; one writer; one independent grader; at most one retry; a human-reviewed patch artifact.
- **Out of scope:** automatic push, PR or merge; self-created tasks; learned policy.

Jev classifies the task and signals ambiguity. Code chooses among explicitly allowed routes ([M1's route set](architecture.md#what-we-reuse-from-the-router)); in M1b there is only one fixed route. The independent grader includes a small, explicit regression suite for the task [CODEX-REVIEW, finding 5]. All fault tests use stand-ins (small fake programs that replace `codex` and the Jev API in tests) with no model calls. *Added in session 2:* the real runs listed below are not stand-ins. Each one uses plan usage, and each one runs under a written limit.

**Where M1 runs** (session 2, [Decision 17](../what-we-could-build.md#decisions-for-the-user), option B). M1 runs on a personal Apple silicon MacBook with macOS 26 or later. Idle sleep must be handled and the disk needs free space for the reserve. The supervisor runs as a LaunchDaemon with `UserName` set to the supervisor account, as [Decision 26d](../what-we-could-build.md#decisions-for-the-user) requires. On the MacBook, these power and disk rules hold (session 2):
- Before a launch, the supervisor takes a "prevent idle sleep" power assertion. It holds the assertion through the attempt, the grading, the export and the cleanup.
- If the supervisor cannot get the assertion, it does not launch.
- On battery power, no new unattended launch starts.
- If AC power is lost during an attempt, the attempt continues under its normal limits. No new unattended launch starts until power returns.
- An assertion cannot prevent a forced sleep, such as a closed lid. It also does not wake a Mac that is already asleep. So queued work may wait.
- A free-disk reserve blocks new attempts (session 2, [Decision 23](../what-we-could-build.md#decisions-for-the-user), second number, option A as amended by Codex, decided on 2026-09-27). It is a reserve, not a plain threshold. An attempt starts only if free space minus that attempt's bounded temporary storage stays at or above 30 GB. The bounded temporary storage covers everything that overlaps during one attempt: the VM's temporary disk, the export, the grading copy and the logs. (session 2)
  - M1a measures this bound, and you revisit the 30 GB number then (see M1a check 1 below). Until the bound is measured, the rule is advisory: no real run relies on it alone. (session 2)
  - The check is part of host readiness. While it fails, the scheduler claims no task, as during a stop. The inbox gets one entry. The entry clears when the check passes again. (session 2)
  - The context for the number: a laptop disk has limited free space. Raw output is kept 90 days. The source archive and the hidden tests are kept for the life of the project. macOS itself needs free space for swap and updates. (session 2)
  - Rejected: a plain threshold of 50 GB (option B) or 30 GB (option C). A plain threshold checks free space only at launch. So an attempt admitted just above it could use up the space that macOS needs before cleanup runs. Codex dropped a 15 GB option, because no measurement supports it. (session 2)

Sleep is not a crash (session 2). Sleep suspends processes, and at wake the same supervisor and workers continue. So the supervisor has a third recovery path, next to startup and the normal loop: the wake event. M1a check 4 tests it. The host for M2 is an entry condition of M2 (see ["What comes after"](#what-comes-after)).

It starts only if all of these hold:
   - the grader classed the failure as retryable;
   - the first attempt did not end by a timeout, a stop or an uncertain termination;
   - a fresh reading between the attempts comes from the same account and the same window, shows a rise of at most 2 points for the first attempt, and shows the window at 80% or less.

   A missing reading, a changed account or window, or readings that cannot be compared block the retry. After the run, the supervisor reports the rise of each attempt and the total of both. If either attempt raised the window by more than 2 points, no further real run starts until you review it. The 15-minute stops cover the worker's run only, not grading and cleanup. The percentages are checked only after each attempt, so they are not a hard limit.

     - **V3.** On the host-only network with the host proxy, only allow-listed hosts are reachable, services on the host are not, and a sentinel secret cannot leave.        *Added (session 3, 2026-09-29, O2, adopted with Codex's conditions; see the OpenShell check):* network ideas borrowed from OpenShell become design notes for the host proxy and for V3:
       - DNS. The proxy answers only for allow-listed names. It authorizes the exact requested name before it forwards the lookup. Arbitrary wildcard subdomains are not allowed, because they can carry secret data. The proxy checks the resolved addresses and connects only to those checked addresses. A short TTL (how long an answer may be cached) alone does not stop DNS rebinding (a name that later resolves to a forbidden address).
       - Blocked destinations. The proxy never connects to loopback, link-local, 169.254.169.254 (the metadata address), private ranges, unspecified or multicast addresses. This holds for IPv4, IPv6 and IPv4-mapped IPv6 (an IPv4 address written in IPv6 form). The one narrow exception is the guest's designated link to the host proxy. Other host services stay denied.
       - Fail closed. A missing or invalid policy prevents the launch. A policy failure also closes existing connections. If the policy process disappears or hangs, traffic is denied, independent of cleanup. Then the VM is stopped and the uncertain work is quarantined. A reconnect never silently resumes the attempt.
       - The policy file. It is one strict, versioned JSON file in a root-owned folder, read with the standard library only. Duplicate keys, unknown fields, unsupported versions, and too much size or depth are rejected. A root-owned boundary file that only the admin account changes limits it. A plain Python check compares normalized host, port and protocol permissions, not strings, to show that the active allow-list stays inside the boundary. Both files, their parent folders and the checker are protected. The hash of the checked policy is bound to the attempt, and exactly those bytes are enforced. The policy does not change during an M1 attempt.
       - Every security control that acceptance relies on enforces from the start. Audit-only mode is only for explicit observation experiments.
       - Telemetry (usage data that a tool sends to its vendor). Every tool is checked for telemetry that is on by default: host daemons, helpers and guest CLIs. A guest allow-list does not limit a host daemon.
       - Denial records. V3 needs structured denial records now. They hold the attempt id, the policy hash, the reason and the positive-control results. They hold no raw credentials and no request bodies. A standard event format (OCSF, a standard JSON format for security events) waits for the evidence-log design.
       - *Blocking before V3 is accepted (Codex):* in the encrypted-relay design, the proxy does not terminate TLS, so subscription tokens stay out of the host proxy. So the proxy cannot see the HTTP Host or `:authority`, the paths or the bodies. SNI (the hostname in the TLS handshake) is not the HTTP authority. V3 therefore needs precise pass criteria for this design and tests of the required provider endpoints. The limitation is recorded: the relay has no domain-fronting check (this concerns the domain-fronting path in the list above). It is never solved by decrypting subscription traffic. An allow-list cannot guarantee that secrets never reach an allowed service.

      - a stop request sent while the supervisor restarts after a crash, with a worker still running: at startup the supervisor ends or finds the leftover worker before its first scheduler pass, and no launch happens before the stop is recorded. If the supervisor does not answer, the client says so and names the fallback: stop it through the admin account.

      With the supervisor stopped, a client request changes no state. The startup check fails when the socket file, an exchange folder or a folder above them has an unexpected owner, mode or ACL entry. Each exchange folder must be mode 700 with one ACL read entry for its one reader. The LaunchDaemon file must set `UserName` to the supervisor account.

    M1a runs test 29 in the stand-in steps of the boundary spike, before the probe run; M1b runs it again on the release copy of the supervisor code (and the bridge code, if built).
