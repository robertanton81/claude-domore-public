# Architecture and subscription policy


> Part of the claude-domore design, 2026-09-26. Status: proposal, nothing built. The overview is [what-we-could-build.md](../what-we-could-build.md). The detailed design of the recommended engine: driver and language, components, the task state machine, side effects and safe resume, verification and containment, budgets, provider adapters, reuse from the router, and the subscription and policy position.

## Recommended architecture

The principle: ordinary code owns state transitions and permissions; models propose work and produce artifacts [CODEX]. Everything below is *design inference* unless a source is named.

### Driver and language

The driver is the deterministic supervisor. An interactive Claude Code session is the planning front-end. It helps write task specifications, drafts answers to clarification requests and can submit tasks, but it does not own state [CODEX]. It cannot approve anything either (see "Human-only actions" below).

**Where it runs.** On a laptop, the supervisor cannot run while the computer sleeps. Desktop scheduled tasks have the same limit [PLAT]. The host also sets the sandbox backend: Seatbelt on macOS, or bubblewrap on Linux, where Ubuntu 24.04 also needs an AppArmor profile [R-README]. AppArmor is a Linux security module that limits what each program may do. OpenAI advises one Codex `auth.json` per runner [FIT]. On each host, the boundary test suite and `codex login status` (run under the worker account; see ["OS accounts"](#os-accounts)) must pass before the first unattended launch.

*Decided in session 2 ([Decision 17](../what-we-could-build.md#before-m1-before-a-later-phase-of-m1), option B, 2026-09-27):* M1 runs on a personal MacBook. It needs an Apple silicon Mac with macOS 26 or later. Power and sleep rules must handle idle sleep, and the disk needs enough free space for the free-disk reserve. The supervisor runs as a LaunchDaemon with `UserName` set to the supervisor account, as part 26d requires (see "Checks" under ["OS accounts"](#os-accounts)).

**Power rules on the MacBook (session 2).**
- Before a launch, the supervisor takes a "prevent idle sleep" power assertion. A power assertion is a request to macOS to keep the machine awake.
- It holds the assertion through the attempt, the grading, the export and the cleanup.
- If it cannot get the assertion, it does not launch.
- On battery power, no new unattended launch starts.
- If AC power is lost during an attempt, the attempt continues under its normal limits. No new unattended launch starts until AC power returns.
- An assertion cannot prevent a forced sleep, such as a closed lid. It also does not wake a Mac that is already asleep. So queued work may wait.
- A free-disk reserve blocks new attempts (session 2; Decision 23, second number). An attempt starts only if free space minus that attempt's bounded temporary storage stays at or above 30 GB. See "A free-disk reserve blocks new attempts" under "Budgets and quotas in subscription units".

**The M2 host is an entry condition of M2 (session 2).** Before M2, you measure one representative week on the MacBook, including idle periods. You compare its continuous awake-and-powered windows with a written M2 queue target. The target includes grading and cleanup time. The measured week also records disk use, and you compare it with the free-disk reserve (session 2). Keep the MacBook for M2 only if the windows meet the target. Otherwise M2 runs on a dedicated always-on Mac, for example a Mac mini on macOS 26 or later, with the same design. On that Mac the boundary suite and the login checks run again before the first unattended launch.

**Rejected hosts (session 2).**
- A dedicated Mac from the start (option C). It is not a simple move of the same design. Over SSH forwarding, `getpeereid` names the SSH daemon instead of the real caller, and file descriptors cannot be passed. So parts of 26d would change. Approvals would also first need a physical visit to that Mac.
- A Linux host (option D). It would reopen Decisions 26a to 26d.

**Sleep and wake (session 2).** Sleep is not a crash. Sleep suspends processes, and at wake the same supervisor and the same workers continue. So the supervisor has a third recovery path, next to startup and the normal loop: the wake event.
- *Detecting wake.* There are two candidate methods. The first is Apple's sleep and wake notifications (`IORegisterForSystemPower`, Apple QA1340). The second uses only the standard library: it watches for a jump between wall-clock time and the monotonic clock. On macOS, `time.monotonic` does not advance during sleep, while `time.time` does. The M1a checks decide which method is used.
- *After a wake.* Every running attempt is treated as uncertain. No export or grading starts until no process of that attempt still runs. Anything uncertain is quarantined (see component 4 in "The eight components" and `effect_unknown` in "The task state machine"). Nothing is retried automatically. Before any launch, the supervisor reads the quota again and checks again that the unattended authorization has not expired.
- *Tests.* A new M1a check puts the Mac to sleep during a stand-in attempt and during a grading, with the assertion active. It checks wake detection. It checks that surviving processes are found without assuming that the supervisor resumes first. It checks that no export or grading starts before the survivors are stopped, that uncertain effects are quarantined, and that nothing is retried automatically. It checks that the quota and the authorization expiry are checked again after wake. M1b repeats this check against the real state layer. The crash tests of V4 do not cover sleep.

**The language is your trade-off.** Other languages, such as Go or Rust, were not compared: none can reuse the router's tested code without a bridge or a port, and neither consult proposed one.

- The bridge is built only if V1, V2 or V5 fails and the grader stays on the host's Seatbelt boundary.
- Before the Node copy is dropped, the Python snapshot and hash port must pass a differential test. The same fixture folders must give the same hashes and the same binding results as the pinned Node copy.

**The bridge contract** (Python option, only if M1a needs it). The bridge has three calls: `wrap(argv, options) → argv` builds the bounded command; `snapshot(dir) → hash`; `grade(task, snapshot) → evidence`. Python spawns the worker and owns its whole process tree, so a bridge crash cannot leave workers that no one tracks. How the supervisor contains every process in that tree is described under component 4, because a process group alone is not enough. A version mismatch or a bridge crash stops the launch.

### The eight components

The list comes from [CODEX]; the descriptions are design inference.

1. **Task admission and clarification.** A task enters as `proposed`. Admission checks for acceptance criteria, allowed paths and a named repository; Jev adds ambiguity signals. Admission also bounds the task size in terms code can count, such as files touched and expected diff size. The reason: the 80% time horizon is 4 to 6 times shorter than the 50% horizon, and [ACAD] advises units well below the reliable horizon [metr-time-horizons-2026]; the bound itself is *design inference*. Missing criteria produce a clarification request. At first only you create tasks. The engine may propose tasks, but it must not create easy work to raise its own success rate [CODEX].
2. **Durable state and scheduler.** A SQLite database with tables for tasks, attempts, events, effects, approvals, evidence and policy versions. The supervisor writes each state change and its event record in one transaction [CODEX]. The scheduler picks only human-approved tasks with satisfied dependencies [CODEX]. **Engine state lives outside every worker's write set:** the database, approval records, evidence, quota readings, the lineage log, the stop file and hidden checks. Codex asked for this: "Keep the supervisor database, approval records, and grading control files outside worker write access" [CODEX]. A worker's writable data folder is a new scratch folder for each attempt, never the engine's data folder. Engine state is also outside the write set of the planning session, because the supervisor runs under its own OS account (see ["OS accounts"](#os-accounts)).
3. **Provider adapters.** One per way of running a model. Each builds the exact command, cleans the environment, checks the login mode and parses the result. Cleaning means an allow-list of variables: never a deny-list, and never a wiped environment. The launcher sets `HOME`, `CODEX_HOME` and `PATH` for the worker account explicitly: `HOME` and `CODEX_HOME` point to the worker account's own folders, and `PATH` holds only the root-owned runtime folder and the system folders. It never passes the supervisor's own values, because they would point Codex at the wrong account's folders. Version-manager shims (small launcher programs) for `node` and `codex` sit in the daily account's home folder, and running them with a wiped environment started about 7,800 processes in a router test run [R-CODE: router `.claude/CLAUDE.md`]. The real files behind the shims are in the home folder too (see "Code that the accounts run" under ["OS accounts"](#os-accounts)). So the adapter runs only the copies in the root-owned runtime folder, by absolute paths that the supervisor pins at startup, and a test puts a stand-in first on `PATH`, as the router's tests do ([added test 23](milestone-1.md#tests-this-document-adds)). Each adapter also applies the shared write rule of [Decision 25](../what-we-could-build.md#decisions-for-the-user) with its own provider's settings (session 2). The Codex adapter sets `approval_policy="never"` and keeps the login volume outside every writable root. The Claude adapter, which is off by default, sets fail-closed sandbox settings and `Edit(...)` deny rules, and it switches off MCP write routes that no probe has tested. The details are under ["Provider adapters"](#provider-adapters) and "Two write routes per CLI" under ["Verification"](#verification-and-what-the-containment-really-covers).
4. **Workspace and process supervisor.** A disposable workspace export per attempt, in a new work folder of the worker account (see "How files pass between accounts" under ["OS accounts"](#os-accounts)). A workspace is never reused while a worker's termination is uncertain [CODEX]. Each attempt folder, named by the attempt id, holds the process record and the worker's `--json` output. Both are written before the intent record is marked "launched", following the router's detached-runner pattern [R-README]. The raw output falls under the store inventory in ["Output stores and retention"](#output-stores-and-retention). The write rule for every worker CLI is decided (session 2, Decision 25). Which containment path each CLI uses is still chosen in M1a, after the stand-in steps (see "Verification").

   **Containing every descendant** [CODEX-REVIEW, finding 6]. The router tracks a worker by its process group: the worker and the processes it starts, which the operating system can signal together. The router signals the group and waits until the group is empty [R-CODE: `scripts/codex-job-runner.mjs`]. A process group does not hold every descendant. Any descendant can call `setsid()` and start its own session. (A POSIX session is a set of process groups. `setsid()` makes the caller the leader of a new session and of a new process group.) Python exposes this call as `os.setsid` (checked 2026-09-26 on Python 3.14.3). A signal to the old group does not reach such a process, and an empty old group does not prove that every writer ended. So the supervisor needs a mechanism that a descendant cannot leave, or a check that finds escaped descendants (*design inference*):
   - **A dedicated worker OS account, used by one attempt or one grading at a time.** The worker runs under a user id that only workers use. The confined candidate process of the grader (component 5) runs under the same account. So the account runs one attempt or one grading, never both at once, and the check that no process of the account is left runs after each grading as well as after each attempt. Without this rule, in M2 the end of attempt B could kill the candidate process of grading A, and a candidate descendant that started its own session could keep the account busy while attempt B runs. M1 and M2 run one writer at a time and serialize Codex jobs per `auth.json`, so one account is enough. If M2 needs a grading to overlap an attempt, the candidate process gets its own account instead. Parallel attempts in a later milestone would need one account each. A process that is not root (the super-user) cannot change its real user id (checked 2026-09-26 in the macOS `setuid(2)` manual), so "no process of this user id is left" covers every descendant. The command `ps -U` lists processes by real user id (checked 2026-09-26 in the macOS `ps` manual). To end them, a launcher that runs as the worker account calls `kill -KILL -1`. For a caller that is not root (the super-user), this sends the signal to every process with the caller's user id, except the caller itself (checked 2026-09-26 in the macOS `kill(2)` manual). A set-user-ID program such as `sudo` (a program that runs a command as another user) can change the user id, so the worker account gets no `sudo` rights. This works on macOS and Linux. On macOS it is the only mechanism in this list that can prove termination.

     **Processes of the worker account that are not descendants** (*design inference*). "No process of this user id is left" also counts processes that the worker did not start, and it misses processes that start later. Two kinds matter:
     - **System helpers.** macOS may start per-user helper programs for an account through launchd, the macOS service manager (possible, not verified for an account with no login session). Such a helper would keep the check from ever passing. So the check skips a process only when its executable path is on an exact list of system helpers that M1a records, and its parent is launchd (process id 1). The list never holds a shell, an interpreter or any other program that runs a command it is given, because a scheduled job could start such a program with launchd as its parent.
     - **Scheduled jobs.** A job that a worker schedules through cron, `at` or launchd starts later, after the check has passed, and it can write the next workspace. So the worker account must not schedule jobs. Its name goes into the deny files for cron and `at`; the rules for these files are in the `crontab` and `at` manuals. launchd is a third way. It loads agents from `~/Library/LaunchAgents` at login, and `launchctl submit` can start a program without any configuration file (checked 2026-09-26 in the `launchctl` manual). The sandbox keeps the model's commands and the candidate process from writing the worker's home folder, so they cannot add a file to `~/Library/LaunchAgents`. The CLI's own edit tool is a second write route there. The probe matrix must show that this route is denied too (session 2; see "Two write routes per CLI" under ["Verification"](#verification-and-what-the-containment-really-covers)). Whether `launchctl submit` works for an account with no login session was not checked. So after each attempt and each grading, the launcher also checks that the worker account has no launchd job, no crontab and no queued `at` job. [Added test 26d](milestone-1.md#tests-this-document-adds) schedules a delayed job.

     **What it means for Codex** (*design inference*; it follows from the worker account chosen for [CODEX-REVIEW, finding 6], which itself says nothing about Codex logins). Codex runs under the worker account, so its login and its session files live in that account's `CODEX_HOME` (the folder where Codex keeps its login and session files). The launcher sets `CODEX_HOME` to that folder (component 3). You run `codex login` once under that account, so it holds its own copy of your ChatGPT login. That makes one runner with one serialized job stream, which is what OpenAI advises [FIT]. Whether two logins of one ChatGPT account, in two OS accounts, refresh their tokens without conflict is not checked. The Codex process itself must write `CODEX_HOME`. The commands that the model runs must not. Under Path A, Codex's own sandbox denies them writes outside the workspace; the router's live probes showed this for outside writes [R-LOG]. The model has a second write route (session 2): Codex's own edit tool, `apply_patch`. Codex checks those edits against its writable folders in its own code, not through the OS sandbox. So the probe matrix checks both routes for `CODEX_HOME` ([added test 20b](milestone-1.md#tests-this-document-adds); see "Two write routes per CLI" under ["Verification"](#verification-and-what-the-containment-really-covers)). After the attempt, and only when no process of the worker account is left, the supervisor copies the quota reading and the thread id into its own store. It also copies the attempt's session files into the attempt folder, which only the supervisor account can read, and checks each copy against a hash of its original. It can read the originals through an ACL read grant. (An ACL, access control list, is a list of extra access rules on one file or folder, next to its owner, group and mode bits. See "How files pass between accounts" under ["OS accounts"](#os-accounts).) Then the launcher, which runs as the worker account, deletes the originals. So the next attempt can neither read nor change them, and the quota readings come from the supervisor's copies. Under Path B this does not help: the outer boundary applies to Codex itself, so a write rule for `CODEX_HOME` would apply to the model's commands too (see "Verification").
   - **On Linux, where available,** a cgroup: a kernel group that holds a process and all its descendants and can stop them together. The router's bubblewrap boundary also passes `--unshare-all` and `--die-with-parent` [R-CODE: `scripts/lib/execution-boundary.mjs`]. Whether these flags hold every descendant was not checked here, and the router's tests do not check it.
   - **As a fallback, a check across the whole OS boundary.** The supervisor lists every process and treats any process whose working folder or open files are inside the workspace as a survivor. This check can miss a process that holds no file open, so it can detect survivors but never prove termination. With this check alone, every workspace would be quarantined, so it only adds detection on top of one of the two mechanisms above.

   A process id (PID) can be reused: after a process ends, the operating system can give its number to a new, unrelated process. So the supervisor identifies a process by its PID together with its exact start time (`ps -o lstart`), or by the attempt's user id, never by a PID alone. When the supervisor dies, workers can keep running: the router starts its runner detached on purpose, so that a job outlives the command that started it [R-CODE: `scripts/orch-codex.mjs`]. On restart, the supervisor finds survivors through the same mechanism, not from its own memory. **When termination cannot be established, the workspace is quarantined:** it is never reused, it is not graded while the doubt remains, and it is kept for inspection. The task goes to `effect_unknown`. Reconciliation may move it on to `checking` only when the mechanism later shows that every process of the attempt ended. The M1a feasibility checks choose the mechanism before the process interfaces are written. [Added test 26](milestone-1.md#tests-this-document-adds) checks it: in M1a on a throwaway prototype, for detection, ending and quarantine; in M1b again with the real state layer, for the move to `effect_unknown`, the rule that the grader never runs on a workspace that a survivor can still change, and a restart of the real supervisor.

   **Network egress on the VM path** (session 3, 2026-09-29; O2, adopted as design notes with Codex's conditions; private record). Egress means outgoing network traffic. On the VM path, the host proxy on the host-only network gives the egress allow-list ([Decision 26](../what-we-could-build.md#before-m1-before-a-later-phase-of-m1), part 26b), and [M1a check V3](milestone-1.md#scope) tests it. These notes come from the OpenShell check. They are rules for the host proxy and for V3:
   - *DNS answers only for allow-listed names.* The proxy authorizes the exact requested name before it forwards a lookup. Arbitrary wildcard subdomains are not allowed, because a subdomain name can carry secret data out. The proxy validates the resolved addresses and connects only to those validated addresses. A short TTL (the time that a DNS answer stays valid) alone does not stop DNS rebinding (a name that later resolves to a different, internal address).
   - *Hard blocks on the proxy's outgoing destinations.* Loopback (the host's own addresses), link-local (addresses valid only on the local network link), 169.254.169.254 (the metadata address), private ranges, unspecified and multicast addresses are blocked. This holds for IPv4, IPv6 and IPv4-mapped IPv6 (IPv6 addresses that carry an IPv4 address). One narrow exception: the guest's designated link to the host proxy. Other host services stay denied.
   - *Fail closed* (when a control fails, traffic is denied, not allowed). An invalid or missing policy prevents the launch. A policy failure also closes existing connections. If the policy process disappears or hangs, traffic is denied independently of cleanup, the VM is stopped and the uncertain work is quarantined. A reconnect never silently resumes the attempt.
   - *One strict policy file.* The egress policy is one versioned JSON file in a root-owned folder (M1 uses only the standard library). The parser rejects duplicate keys, unknown fields, unsupported versions, and too much size or depth. A root-owned boundary file limits the policy, and only the admin account changes it. A plain Python check compares normalized host, port and protocol permissions, not strings. It shows that the active allow-list stays inside the boundary. Both files, their parent folders and the checker are protected. The hash of the checked policy is bound to the attempt, and exactly those bytes are enforced. The policy does not change during an M1 attempt.
   - *Enforce from the start.* Any security control that acceptance relies on enforces from the start. Audit-only mode (a mode that only records what it would block) is only for explicit observation experiments.
   - *Telemetry.* Every tool is checked for telemetry that is on by default: host daemons, helpers and guest CLIs. A guest allow-list does not limit a host daemon.
   - *An M1a check item, not yet a design choice.* M1a verifies whether Apple `container` can start a guest with no network device and a usable vsock channel (a host-guest channel that does not use the network). It also tests relay identity, other host services that the guest can reach, and whether the inner sandbox still works. (The relay is the host process that carries the guest's connections.) A guest with no network device removes direct paths, but it does not prove the relay safe. This item is not mandatory if the current internal-network design passes V3.
   - *Denial records.* V3 needs structured denial records now: the attempt id, the policy hash, the reason and the positive-control results. They hold no raw credentials and no request bodies. OCSF event classes (a standard JSON format for security events) are considered later, at the design of the evidence log.
   - *What an encrypted relay can check* (Codex's blocking clarification before V3 acceptance). An encrypted relay does not terminate TLS (it does not decrypt the traffic), so subscription tokens stay out of the host proxy. So it cannot see the HTTP Host or `:authority` header, the paths or the bodies. SNI (the hostname in the TLS handshake) is not the HTTP authority. V3 lists a domain-fronting probe (a request whose SNI names an allowed host while the HTTP host inside the encrypted traffic names another). So V3 needs precise pass criteria for the encrypted-relay design, tests of the required provider endpoints, and a recorded limitation: no domain-fronting check. This is never solved by decrypting subscription traffic. An allow-list cannot guarantee that secrets never reach an allowed service.
   - Team view: Claude adopt, Codex adopt with the conditions above, Jev A (0.98).
5. **Independent verification.** Reused from the router: the confined snapshot, hash binding, and the grader boundary without network [R-README]. New work: restoring trusted tests before grading, the allowed-path check, `.git` handling, the patch artifact, and the split of grading into two processes (see "What M1 adds" below). The router's grader contract is narrow [R-README], [R-CODE: `scripts/lib/executable-grade.mjs`, `scripts/lib/eval.mjs`]:
   - one copied `.mjs` file, with no sibling helper files;
   - reads only its control folder, the Node runtime folder and system folders;
   - no network and no inherited credentials;
   - snapshots refuse any link and stop at 10,000 entries or 100 MiB;
   - the export (`git archive`) has no `.git` folder, so Codex needs `--skip-git-repo-check` ("Allow running Codex outside a Git repository", checked 2026-09-26 with `codex exec --help`) or a fresh `git init` in the export.

   **What the router's grader does not prove** [CODEX-REVIEW, finding 4]. Checked 2026-09-26 in `verifyWorkspace()` [R-CODE: `scripts/lib/executable-grade.mjs`]:
   - The grader runs as `node grader.mjs <snapshot>`. Its working folder is the snapshot copy of the candidate, inside the grader's control folder.
   - It may read the whole control folder, which also holds `grader.mjs` itself. It may write only its scratch folder, and it has no network.
   - The grader has a time limit and an output limit. The time limit is `verify.timeoutS`: 30 seconds by default, at most 600. The output limit is 8 MiB, the default of the router's process runner `runOne` [R-CODE: `scripts/lib/eval.mjs`]. The status is `passed` only when the exit code is 0 and neither limit was hit.
   - The evidence keeps only a hash of the output. It does not record which checks ran.

   Two attacks follow. First, if the grader imports candidate code into its own process, that code can end the process with exit code 0 before any assertion runs, and the grade is `passed`. Second, candidate code that the grader runs, in the same process or as a child, has the grader's read rights, so it can read the hidden checks in the control folder. Worker-side tests of hidden files ([added test 16a](milestone-1.md#tests-this-document-adds)) cover neither case, because they run during the attempt, not during grading.

   **What M1 adds** (*design inference*). M1 splits grading into two processes:
   - **A protected checking process.** It holds the hidden checks and the expected results, and it computes the verdict. The candidate cannot read or write anything it holds.
   - **A separately confined candidate process.** It runs the candidate code on the inputs that the checker sends. It runs in a new work folder of the worker account, which holds a copy of the candidate snapshot and a scratch folder. It can read only that copy, not the control folder, and it has no network. It runs under the worker account, never under the supervisor account, so candidate code cannot read the database or the Jev key either. The worker account runs one grading or one attempt at a time (component 4), and the check that no process of the account is left runs after the grading too (see ["OS accounts"](#os-accounts)). It returns values; the checker compares them with the expected results in its own process. *On the VM path of Decision 26b, this process runs in a fresh grader VM instead of the worker account. The checker and the hidden checks never enter that VM ([M1a check V5](milestone-1.md#scope); session 2 review).*

   The checker has a fixed list of expected check ids. A check counts only when the checker itself records it as completed and passed. A `passed` verdict needs every expected check completed and passed; an exit code of 0 alone is not enough. Candidate output is untrusted data: the checker never counts text such as "12 tests passed" that candidate code printed. The evidence lists the completed check ids next to the hashes. [Added test 24](milestone-1.md#tests-this-document-adds) runs candidates that exit early, read grader files and forge test output. The bridge's `grade` call therefore returns this richer evidence. The router's snapshot, hash binding and boundary code stay as they are; the split into two processes is new code.
6. **Budget and quota control.** Tracks provider windows, attempts, time, Jev requests and spending, and learning spending separately, and reserves capacity before launch [CODEX]. Details below.
7. **Human approval inbox.** Lists clarification requests, candidates awaiting review and blocked tasks, each with its reason. Since session 2 it also lists proposals to add a repository to the Jev allow-list (Decision 14), an entry when a Jev counter limit is reached (Decision 23), and, from M2, the findings of the advisory review next to their patch (Decision 19). Each approval binds to an artifact hash and a requested action [CODEX].
8. **Learning experiments and artifact registry.** Learned artifacts (routing tables, experience records, prompts) with versions, provenance and rollback. Learned artifacts are versioned inputs. Components 1 to 3 read them only inside ranges fixed in code. - **A terminal prompt is not enough.** A terminal does not show that a human is typing. Software can create a pseudo-terminal: a pair of connected endpoints that look like a terminal to the program on one side, while another program types on the other side. Python's `pty` module does this with `pty.openpty()` and `pty.spawn()` (checked 2026-09-26 on Python 3.14.3). So an agent whose direct tool call is refused could succeed through a small wrapper.
- **The rule.** An approval counts only when it carries an approval identity or a signing capability that neither the workers nor the planning session hold. Two ways meet this rule (*design inference*):
  - **A separate OS user for approvals.** Only you know its password, and the account that runs the planning session cannot act as it without that password. This premise needs an account that cannot become root (see ["OS accounts"](#os-accounts)). The approval command runs as that user and sends the approval through the input socket. The kernel reports the caller's user id for each connection, and the supervisor accepts human-only decisions only from the approval account (see "The input socket and the exchange folders" under ["OS accounts"](#os-accounts); session 2). The database stays outside every worker's and the planning session's write set, because it belongs to the supervisor account. **How you reach the approval account:** only through its own login session, for example through macOS fast user switching (which keeps a second user's desktop session open next to yours), never through `su` or `sudo -u` in a terminal of your daily account. The reason: a process of your daily account might drive such a terminal and type approvals into the approval shell, for example through AppleScript's `do script` if it has the macOS Automation permission (not verified). The approval command can refuse to run outside a login session of the approval account; how it checks this on macOS is not verified. A hardware security key that needs a touch for each approval blocks the same path without that check, because software cannot give the touch. [Added test 17e](milestone-1.md#tests-this-document-adds) checks this route.
  - **A signing key that only you can use.** Each approval is a signed statement. The private key sits under the separate approval user, or on a hardware security key that needs a touch. The supervisor holds only the public key. `ssh-keygen -Y sign` and `ssh-keygen -Y verify` exist in the OpenSSH that ships with macOS (checked 2026-09-26). *Correction (session 2):* Apple's `/usr/bin/ssh-keygen` knows the key type `ed25519-sk` but cannot make or use such keys: it stops with "No FIDO SecurityKeyProvider specified" (checked 2026-09-26). An OpenSSH build with libfido2 is needed, installed in the root-owned runtime folder. *Note (session 3, 2026-09-29; R3 of a private research record):* the correction holds only without a provider. Apple's `ssh-keygen` (OpenSSH_10.3p1) documents `-w provider` and tries to load `SSH_SK_PROVIDER`. It also has the entitlement `com.apple.security.cs.disable-library-validation`, which lets it load libraries that Apple did not sign (all checked locally 2026-09-29). So with a self-built provider library, Apple's `ssh-keygen` may make and use such keys. M1a check 2 tests this. The decision builds only that provider library, not a full OpenSSH (see "What goes into the runtime folder now" under ["OS accounts"](#os-accounts)). Python's standard library has HMAC (a keyed hash; whoever checks it also holds the secret) but no public-key signature check, so the supervisor would call `ssh-keygen -Y verify`.
- **No replay, and what is signed** (session 2 review). For each inbox entry, the supervisor writes one canonical approval record in a fixed format. It holds:
  - the task id, the repository and the action;
  - the artifact hash;
  - the specification version (the hash of the acceptance criteria and the allowed paths);
  - the limits that the action grants (attempts, time, budget);
  - the inbox entry id and its version;
  - a nonce: a single-use random number that the supervisor issues for this one entry;
  - the required role, `high` or `low` (session 2). The supervisor sets it from its own state when it creates the entry (see the UV policy below).

  The approval command runs from the root-owned runtime folder. It reads the record and the artifact, and it shows every field and the full patch. It computes the hash from exactly the bytes it shows, and only then asks for the touch (and, for a high-role record, the PIN; session 2). It signs the hash of those bytes. The supervisor recomputes the hash from its own database. It refuses the approval if any field differs, or if the entry changed after the nonce was issued. In one transaction, the supervisor marks the nonce used, stores the new signature counter and applies the state change. An old approval, an approval for another artifact, or a second use of the same nonce is refused.
- **Safe display** (session 2 review). The approval command shows every control character as a visible escape, for example `\x1b`. This covers C0 except newline and tab, DEL, C1, and the Unicode bidirectional controls U+202A to U+202E and U+2066 to U+2069. So candidate text can neither hide lines nor rewrite them on screen. The command handles one request at a time. Only the approval account can read the key-handle files of the FIDO2 key (one per credential since session 2), so no other account can request a signature with either credential.
- **Tests.** [Added test 17](milestone-1.md#tests-this-document-adds) tries the direct tool call, a pseudo-terminal that a program creates, a direct write to the database, the replay of an old approval, and a daily-account process that drives an approval shell in a terminal of your daily account. The M1a feasibility checks run it on a throwaway prototype before the state interfaces are written, and M1b runs it again on the real state layer. [Decision 26](../what-we-could-build.md#decisions-for-the-user) asks which approval identity to use, and only you can set it up.

An approval bound to an artifact hash does not by itself prove that a human made it; the approval identity does.

It reads the flag and the counter from the signature itself, because `ssh-keygen -Y verify` checks the cryptography but not the flag (found in the OpenSSH source by the tools round, a private research record, section 4). Counter policy (decided in session 2, Decision 26c part 1, option C): the policy is fixed per key at enrollment. If the key shows a working counter at setup, every accepted signature must carry a counter higher than the last accepted one, and a later counter of 0 counts as a failure. **UV policy** (decided in session 2, 2026-09-26, Decision 26c part 2, option C). UV means user verification: a PIN on the FIDO2 key. Every human-only action needs a touch. Only high-impact actions also need the PIN.
- *Two credentials.* The key holds two credentials. You make both in the approval account, with the physical key plugged in, and the attestation of each is kept. The "high" credential is made with `ssh-keygen -O verify-required`, so it needs a touch and the PIN. The "low" credential is made without it, so it needs only a touch. Each credential has its own key-handle file. Both are pinned in the supervisor's allowed_signers file with their role (since session 3, that file is in `/opt/claude-domore/approval-policy/`; see "How the signature is checked" below). Only the admin account can replace either one, and a replacement re-runs added test 17f.
- *High-impact actions* need the high credential and the UV flag:
  - approving a task;
  - accepting a patch;
  - a launch authorization that allows unattended runs;
  - authorizing unattended runs: renewing the unattended authorization before or after it expires (session 2). The drift report can stop execution, but it can never renew this authorization (see "Unattended authorization" under "The task state machine");
  - an attended run while a stop for security drift is recorded (session 2). The approval names one run and its limits (see "Stop requests" under ["OS accounts"](#os-accounts));
  - unblocking a task, because it can return a task to work, even after a security block;
  - a restart after a stop;
  - cancelling a task. Only you cancel a task, by [Decision 31](../what-we-could-build.md#decisions-for-the-user) (session 2). A cancellation proposal from the planning session is only a draft. Your cancel itself needs this signature;
  - a clarification answer that changes the task's scope. The changed scope then needs a fresh high approval before any work runs;
  - adding a repository to the Jev allow-list ([Decision 14](../what-we-could-build.md#before-m1-before-a-later-phase-of-m1), session 2). The approval screen says that summaries and excerpts can reveal confidential content even when no secret is recognized. A removal needs no approval: your daily account requests it through the input socket, and it takes effect at once. A removal stops future sends. It cannot delete what TypeSafe already holds. The fixture repository of M1b is added the same way, with the high credential.
- *Low-impact actions* need only the low credential:
  - a clarification answer that does not change the task's scope;
  - a launch authorization for one attended run within fixed limits, which grants no unattended continuation. This does not apply while a stop for security drift is recorded. Then an attended run needs the high credential (session 2).
- *The emergency stop never needs a PIN.* It is a stop request from your daily account through the input socket, not an approval.
- *Who sets the role.* The supervisor decides the required role from its own state and the signed action. It never takes the role from a label in the request, from the caller or from Jev. It writes the role into the canonical approval record when it creates the inbox entry. It computes the role again when the signature arrives, and refuses the signature if the two differ (*design inference*). An action that the supervisor does not know needs the high credential, or it is refused.
- *The UV flag.* The supervisor reads the UV flag from the signature itself, as it does for the UP flag. The key's verify-required setting alone is not proof.

### The task state machine

States from [CODEX]; guards are design inference.

`proposed → needs_clarification | ready → running → checking → verified_candidate → awaiting_approval → accepted`, plus `retryable`, `blocked`, `cancelled` and `effect_unknown`. (`|` means "or": a proposed task goes either to `needs_clarification` or to `ready`.)

| From | To | When | Guard in code |
|---|---|---|---|
| proposed | needs_clarification | Criteria missing, or an ambiguity signal above a low threshold | Always allowed |
| needs_clarification | proposed | You answered, through the human-only channel | New specification version stored |
| proposed | ready | You approved | Approval binds to the specification version; dependencies met. If Jev was down, the inbox shows "ambiguity not checked" |
| ready | running | Scheduler claims the task | Atomic claim with a fencing token (an increasing ownership number; see below); launch count below the authorized launch limit, checked and raised in the same transaction (see "The retry cap" below); budget reserved; quota known and fresh for this provider; containment available; the host is ready (see "Host readiness" below; session 2, Decision 17); no stop recorded in the stop file (session 2 review), except an attended run with its own approval during a stop for security drift (session 2); for an unattended launch, an unexpired unattended authorization (session 2; see "Unattended authorization" below) |
| ready | blocked | A launch check above fails (`launch_refused`) | The reason is stored: `quota_unknown`, `reserve_line`, `containment_unavailable`, `budget`. The move writes one `launch_refused` event and one inbox entry. An expired unattended authorization is not a reason here: it blocks no task (decided 2026-09-30; see "Unattended authorization" below). The scheduler never claims a `blocked` task, so later passes add nothing |
| running | checking | Worker ended, with any exit code | Snapshot captured; the containment mechanism of component 4 shows that every process of the attempt ended, not only that the process group is empty |
| running | needs_clarification | Worker used the "flag for human" exit | Workspace kept for review |
| running | effect_unknown | Supervisor lost track of the launch, or termination of the attempt's processes cannot be established | Never relaunch automatically; the workspace is quarantined |
| checking | verified_candidate | Grader status `passed`; allowed paths respected | Evidence bound to the snapshot hash |
| checking | retryable | Grader status `failed` in the agent's work; cap not reached | Launch count below the authorized limit |
| checking | blocked | Cap reached, grader status `error`, environmental failure, provider limit, or a secret found in the patch | The reason is stored: `cap_reached`, `grader_error`, `environment`, `provider_limit` or `secret_found` (see "Output stores and retention"). A provider limit pauses; it is not a quality failure [CODEX]. `provider_limit` needs provider evidence, such as Codex's own usage-limit event; a Jev "usage limit" class without it stores `environment` |
| checking | effect_unknown | Grader status `stale`: the workspace changed during grading, so a writer survived | Workspace quarantined |
| running or checking | blocked | A stop request interrupted the attempt or its grading (see "Stop requests" under ["OS accounts"](#os-accounts)) | The containment mechanism of component 4 shows that every process of the attempt or of the grading ended; the reason is `stopped`. Otherwise the task goes to `effect_unknown`. The interrupted launch still counts toward the launch limit |
| retryable | ready | Code picks the next route from those still allowed | Launch count below the authorized limit. Jev suggests; code chooses. If Jev is down, the row for job 3 in the [decision table](jev.md#decision-table-jev-answers-and-failures) applies: retry on the default route within the cap, unless provider evidence shows a usage limit |
| blocked | ready | Automatic, only for the quota reasons `provider_limit`, `quota_unknown` and `reserve_line` | A fresh reading for this provider, taken after the reset, shows room: used + reserved + reserve line ≤ 100. The reserve line is the share of each window kept free for your own work (see "Budgets and quotas") |
| blocked | ready | Every other reason (`cap_reached`, `grader_error`, `environment`, `containment_unavailable`, `budget`, `effect_uncertain`, `secret_found`, `stopped`): only when you unblock the task | Through the human-only channel; your reason is recorded. A reset never moves these tasks. For `cap_reached`, the unblock must carry a new launch authorization with its new limit; without it the task stays `blocked` |
| verified_candidate | awaiting_approval | Human review required (always, at first) | None |
| awaiting_approval | accepted | You approve this artifact for this action | Bound to artifact hash and action |
| awaiting_approval | retryable, blocked, needs_clarification or cancelled | You reject the patch | `retryable` only while the launch count is below the authorized limit; at the limit the task goes to `blocked` with `cap_reached`. You label the rejection reason against the specification and acceptance-contract versions that applied during the attempt: the patch breaks that contract (a grader false pass), the requirement changed after the attempt, or a style preference. Only the first counts as a grader false pass [CODEX-REVIEW, finding 10] |
| any open state | cancelled | You cancel | Workers terminated first. Only through the human-only channel, signed with the high credential ([Decision 31](../what-we-could-build.md#decisions-for-the-user), decided in session 2). A cancellation proposal from the planning session changes no state |
| effect_unknown | running, checking or blocked | Reconciliation: a live worker is found (`running`); the containment mechanism of component 4 shows that every process of the attempt ended, and the workspace is intact (`checking`); still uncertain (`blocked`, reason `effect_uncertain`) | Observed facts only; never to `ready` without a human |

While a stop is recorded, the scheduler claims no task (session 2 review). `ready` tasks stay `ready` and get no `launch_refused` event, and the automatic blocked → ready quota move does not start a launch. The one exception is an attended run that you approved for one run during a stop for security drift (session 2; see "Stop requests" under ["OS accounts"](#os-accounts)).

**Host readiness** (session 2, [Decision 17](../what-we-could-build.md#before-m1-before-a-later-phase-of-m1)). The host is ready when the supervisor holds its power assertion, the free-disk reserve holds (session 2: free space minus the next attempt's bounded temporary storage is at least 30 GB; until M1a measures that bound, this check is advisory; see "A free-disk reserve blocks new attempts" under ["Budgets and quotas in subscription units"](#budgets-and-quotas-in-subscription-units)), and, for an unattended launch, the Mac is on AC power. These are conditions of the host, not of a task. So while one of them fails, the scheduler claims no task, as during a stop: `ready` tasks stay `ready`, get no `launch_refused` event, and need no unblock. The inbox gets one entry per failing condition, and the entry clears itself when the condition passes again. A wake from sleep is handled first by the wake path in "Sleep and wake" under ["Driver and language"](#driver-and-language); only after it has finished does the scheduler check host readiness.

**Unattended authorization** (session 2; [Decision 18](../what-we-could-build.md#before-m1-before-any-code) follow-up, option B, decided 2026-09-26). Your authorization for unattended running expires after a fixed period, and you must renew it. The supervisor enforces the expiry itself:
- The authorization record in the supervisor's database carries an expiry time.
- The `ready → running` guard for every unattended launch requires an unexpired authorization.
- Renewing is "authorizing unattended runs", a high-impact action under [Decision 26](../what-we-could-build.md#before-m1-before-a-later-phase-of-m1), part 26c: a touch plus the PIN (see the UV policy under "Human-only actions"). A renewal without the high credential and the UV flag is refused.
- The drift report can stop execution, but it can never renew the authorization. So a missing or suppressed drift report cannot keep unattended runs going beyond the period.
- The period is a number set under [Decision 23](../what-we-could-build.md#before-m1-before-a-later-phase-of-m1), before M2, because unattended runs start at M2. The suggested starting value is 7 days.
- **What happens at expiry** (decided 2026-09-30: option C with Codex's three conditions; private record). The expiry is a condition of the engine, not of a task. For launching, it works like a stop or a failed host-readiness check:
  - The expiry itself moves no task. `ready` tasks stay `ready`, and they get no `launch_refused` event.
  - The scheduler claims no task for an unattended launch while the authorization is expired. The `ready → running` guard still checks the authorization on every unattended launch. If it finds the authorization expired, no claim is made, and the task stays `ready`.
  - The supervisor records one engine-level event with the reason `authorization_expired` for each expired period, and the inbox gets one renewal entry. Repeated scheduler passes and supervisor restarts add no second event and no second entry. The next expiry, after a renewal, creates a new event and a new renewal entry.
  - Unlike a stop, the expiry ends no worker. A running attempt finishes its current step under the normal limits and is not relaunched (see ["Budgets and quotas in subscription units"](#budgets-and-quotas-in-subscription-units)).
  - After a valid renewal, `ready` tasks can launch again, and every other launch check still applies. The renewal moves no `blocked` task. Each keeps its own way back: the automatic quota rule or your unblock. A renewal never lifts a recorded stop, never resets a launch count and never raises a launch limit.
  - An invalid renewal (see above) is refused, and no unattended launch starts.
  - Why: the earlier text blocked each waiting task with `authorization_expired`, and it was unclear whether a renewal freed them; read literally, each task needed your unblock (found on 2026-09-30, when the diagrams were checked against the docs). A stop and a failed host check already keep tasks `ready`, so the expiry now does the same.
  - Team view: Claude C. Codex C, with three conditions: one event per expired period, tests for the recovery and not only for the refusal, and the stop comparison limited to launching. Jev B at 0.68 (confidence 0.53, a weak lean). You chose C with Codex's conditions.
- Attended runs with their own bounded approval are not affected.

The grader statuses `passed`, `failed`, `stale` and `error` come from the router [R-README]. A task blocked for a quota reason returns by itself only when a fresh reading after the reset shows room; a separate `paused` state would also work. Every other reason needs you, so a reset cannot get around the retry cap or the `effect_unknown` rule. The reason `provider_limit` is set only from provider evidence, such as Codex's own usage-limit event, never from Jev alone. A Jev "usage limit" class without that evidence stores `environment`, which only you can clear. So a real test failure that Jev misreads as a usage limit cannot come back after every reset ([added test 22b](milestone-1.md#tests-this-document-adds)). When containment is unavailable, the supervisor pauses all unattended launches, not only one task. M2 adds `accepted → committing → committed` and `committing → effect_unknown` for local commits; M5 adds the matching push and PR states.

**The retry cap** [CODEX-REVIEW, finding 9]. Several paths lead back to a launch: a rejected patch, an answered clarification, an unblocked task and recovery after a crash. So the cap is not a guard on one arrow; it is enforced at the launch itself (*design inference*):
- Each task has a launch count and an authorized launch limit. In M1 the limit is 2: the first attempt and at most one retry.
- `ready → running` is the only move that launches a worker. In the same transaction as the claim and the launch intent, it checks that the count is below the limit and raises the count by one. A crash after that transaction still counts the launch, even if no worker started; that case goes to `effect_unknown`.
- A new specification version, an answered clarification or an unblock does not reset the count.
- Only a new launch authorization raises the limit. It comes through the human-only channel and names the task, the new limit and your reason, and it is stored as an approval record.
- Reconciliation from `effect_unknown` to `running` adopts a worker that already exists. It is not a new launch, so it does not change the count.

[Added test 27](milestone-1.md#tests-this-document-adds) checks rejection, clarification, unblocking and crash recovery at the cap.

A worker may survive a supervisor crash; whether it does is not tested. [PLAT] lists no option to choose the session id of a `codex exec` run (`claude -p` has `--session-id`). So after a crash, the supervisor finds the Codex session through the thread recorded in the saved output, as the router's runner finds its own thread [R-DEC].

Each attempt records [CODEX]:
- the specification and acceptance-contract versions;
- the base revision and the candidate snapshot hash;
- the attempt id, the worker session id and the execution environment;
- the prompt, policy, retrieved-memory and grader versions;
- budget reservations and consumption;
- claims, kept apart from verified observations.

### Side effects, fencing tokens and safe resume

A side effect changes the world outside the supervisor's database: a model launch, a commit, a push, a PR. Idempotency means that retrying an operation does not create a second effect; attaching an id alone does not provide it. Before each effect, the supervisor stores its intent and a stable operation id, then runs it and records the result [CODEX].

| Effect | Rule [CODEX] |
|---|---|
| Model launch | Reserve attempt id and workspace first. If a crash leaves launch status unknown, inspect runner and session records; do not launch another paid attempt at once. |
| Commit | Only the supervisor commits, only the exact verified tree. Store parent, tree and operation id; after a crash, find the matching commit instead of making another. |
| Push | Task-specific branch; compare the remote revision before any retry. |
| PR | Stable operation marker and branch identity; after a timeout, look for an existing PR; if still uncertain, pause. |

Codex marks the Git-host API guarantees as unverified and warns against promising "exactly once" without provider support [CODEX].

**Fencing tokens.** Each claim of a task gets a higher token. A result that carries an older token is rejected, because it comes from a supervisor that lost ownership. A token does not stop an old worker from writing files; that is why a workspace is never reused while termination is uncertain [CODEX].

**Safe resume.** Resume means reconciling with observed reality, not repeating the last instruction [CODEX]. On resume the supervisor re-checks git HEAD, the snapshot hash, lock ownership and provider limits before it continues [ACAD, implications]. A test kills the supervisor in the middle of each step [resume-means-resume-2026], [safe-to-resume-2026]. A wake after sleep is also a resume point, but not a crash (session 2): the same supervisor continues, and it reconciles as described in "Sleep and wake" under "Driver and language". The crash tests do not cover sleep.

**Approval binding.** An approval names an artifact hash and an action; an approval for one patch does not authorize its replacement [CODEX]. This also answers the rollback attack in [safe-to-resume-2026]. The approval also carries a single-use nonce and the approval identity, so an old approval cannot be replayed (see "Human-only actions").

### Verification, and what the containment really covers

Verification must establish that the intended checks ran, the patch respects allowed paths and operations, trusted tests pass on the captured candidate, regression obligations still pass, and any required review is complete [CODEX]. No model review is required for acceptance ([Decision 19](../what-we-could-build.md#before-m1-before-a-later-phase-of-m1), option B as amended, session 2). From M2, an advisory trial adds a Claude review of Codex patches, in a fresh planning session for each review. The review gives findings only. It never passes or blocks a candidate, never rewrites code and is never a learning reward. The findings arrive as an ordinary draft through the input socket, bound to the patch hash, and the inbox shows them next to the patch. A gate is possible only through a new decision, and not before M5. Rules:
- Public diagnostic tests stay apart from hidden acceptance checks. Workers may add tests; changing the trusted acceptance contract needs separate approval [CODEX].
- Restore test files from the trusted snapshot before grading, and start each trial from a clean checkout [impossiblebench-2025], [anthropic-evals-2026] (*vendor*). The restore acts on a grading copy, never on the candidate or the patch (see "Three artifacts" below).
- Record a pass as "plausible", not "correct" [patchdiff-2025]. An exit code shows that the chosen check passed, not that the specification was complete [CODEX]. Never accept a worker's own "done" [cli-failure-process-2026].
- Keep observed failures, including environment and grader failures, apart from the agent's explanation of the cause [CODEX].
- The worker's brief offers an explicit "flag for human" exit, which moves the task to `needs_clarification`. It cut GPT-5's cheating from 54% to 9% but helped Claude Opus 4.1 much less [impossiblebench-2025] [ACAD].
- The trusted checks include a small, explicit regression suite for the task: existing behaviors near the change that must still work. A patch that fixes the defect but breaks one of them is not a candidate ([added test 25](milestone-1.md#tests-this-document-adds)).

**Three artifacts** [CODEX-REVIEW, finding 11]. A restored grading tree could pass while the exported patch still deletes tests. So the supervisor keeps three artifacts apart and records how they relate (*design inference*):
1. **The candidate tree:** the snapshot of the worker's workspace, with its hash. This is what the worker produced.
2. **The grading tree:** a copy of the candidate tree with the trusted test files restored from the trusted snapshot. The record names the candidate hash and the trusted test-set version that it came from. Only the grader sees this tree.
3. **The deliverable patch:** generated from the approved candidate tree against the base revision, never from the grading tree. Your approval binds to the patch hash, and the record also names the candidate and grading hashes.

The allowed-path check runs on the candidate tree. A candidate that deletes, renames or changes a trusted test file fails it, unless the acceptance contract allows that path; changing the acceptance contract needs separate approval [CODEX]. A test file that the worker added stays in the patch and is listed in the inbox. It is diagnostic only and does not count toward the verdict. [Added test 28](milestone-1.md#tests-this-document-adds) covers added, deleted, renamed and changed test files.

A probe counts only when three things hold [CODEX-REVIEW, finding 7]:
- The worker's event log shows that the probe command really ran. A model that ignores the instruction or never tries the operation gives an inconclusive result, not a pass.
- The probe got the exact denial. The router's live probes recorded `EPERM` for outside writes, shared `/tmp` writes and loopback connections [R-LOG]. A refused connection (`ECONNREFUSED`) can mean that no server was listening, so it does not count.
- A positive control passed: the supervisor ran the same probe as the worker account outside the sandbox, against the same listening server, and every operation succeeded. So each probe target must be a place that the worker account can write or reach at OS level; then only the sandbox can deny the operation. A target that file permissions protect gives `EACCES` ("permission denied") instead, and its positive control cannot succeed.

These three conditions apply to the probes of added tests 16b and 20b, and to every probe of the matrix in "Two write routes per CLI" below (session 2). The reads of [added test 14b](milestone-1.md#tests-this-document-adds) follow their own rule, because they test the account separation, not the sandbox: they must fail for the worker account with and without a sandbox, and their positive control is the same read run as the supervisor account.

**Two write routes per CLI** (session 2; [Decision 25](../what-we-could-build.md#decisions-for-the-user), option A as amended by Codex, chosen 2026-09-27).

*Why two routes.* Each worker CLI gives its model two ways to write a file:
- **The shell route.** The model runs a command. The CLI's OS sandbox covers that command and its child processes.
- **The edit-tool route.** The model uses the CLI's own edit tool. The CLI's own code checks that edit, not the OS sandbox.

The facts behind this (checked 2026-09-27):
- Claude Code's OS sandbox covers only Bash, PowerShell and Monitor commands and their children. Read, Edit, Write, WebFetch and MCP tools are governed by permission rules inside the Claude Code process.
- Codex's OS sandbox covers the commands that Codex starts. Codex checks its own `apply_patch` edits against its writable folders in its code. Codex, as a reviewer in session 2, read `codex-rs/core/src/safety.rs` for this. That is source evidence, not proof for the installed binary.

*The rule.* One acceptance rule holds for every worker CLI: Codex now, and Claude Code once Decision 6 allows it. The enforcement differs per provider. "Identical" means the same denied operations and the same failure handling. It does not mean identical sandbox coverage.

*The inner sandbox.* On the VM path, a worker CLI's own sandbox stays on inside the guest only in full mode. Claude Code's `enableWeakerNestedSandbox` is switched off and does not count. If the full inner sandbox fails to start, that is an explicit fallback trigger. V1 alone tests only that the container starts.

*The probe matrix.* It replaces the single-route V2 probe, which tested only shell writes. It runs once per CLI:
- It runs on the pinned CLI version with the exact launch settings.
- Its targets are harmless copies of the CLI's login and config files.
- It tries shell writes and every enabled writing tool.
- For each route, it tries to create a file, to replace a file and to write through a path alias (for example a link or a second name for the same folder).
- Each probe needs the exact denial, unchanged hashes of the copied files, and a matching success outside the restriction (the positive control).
- A skipped probe is inconclusive, not a pass.
- The matrix runs again after any change of version, settings or tools.
- The worker-account fallback must pass the same matrix.

*Enforcement for Codex.* `approval_policy="never"`, and the login volume stays outside every writable root.

*Enforcement for Claude Code* (only once Decision 6 allows it):
- `sandbox.enabled` true, `failIfUnavailable` true, and `allowUnsandboxedCommands` false.
- Explicit `Edit(...)` deny rules for its credential and config files. Claude Code's documentation says these rules cover all built-in writing tools and hold in `-p` runs and in `bypassPermissions` mode. `Write(path)` is not a supported path rule.
- MCP write routes that no probe has tested are switched off.
- The settings are stored outside every folder that the model can write.

These file rules do not limit child processes or MCP tools. That is why both the OS sandbox and the MCP switch-off are required.

*Failure handling.* If V1 or V2 (the probe matrix) fails for a CLI, that CLI uses the worker-account fallback, with Path A as the default there. If the fallback also fails its matrix, that CLI stays disabled.

*Timing.* The path choice is still made in M1a after the stand-in steps. V1 to V8 all stay mandatory. The result of M1a check 1 stays provisional until the real probe run records every probe. Claude stays off until Decision 6. Its first real run is its own probe run, before any ordinary work. V6 and V7 are restated for Claude before it is enabled.

*Rejected.* A rule for Codex only (option B), because it postpones the shared rule. Accepting Claude's weaker nested mode (option C), because Claude Code's own documentation says it considerably reduces security.

*Not decided here.* Whether to turn on Claude Code's Bash sandbox for your planning session and other sessions as a second layer is a later question. Decision 6 also stays open. **What it does not cover:**
- It is not credential isolation. Worker network and broad host reads stay allowed on purpose [R-DEC], [CODEX].
- It does not hide other archived copies or git history elsewhere on the host [R-README]. A worker can read the original repository of a past failure and its fix commit. Until [added tests 16a and 16b](milestone-1.md#tests-this-document-adds) pass, such tasks can leak their answers.
- The router's worker environment is not safe to copy. `boundWorker()` passes `TYPESAFE_API_KEY`, `CLAUDE_PLUGIN_OPTION_TYPESAFE_API_KEY`, `CLAUDE_CODE_OAUTH_TOKEN` and every `ORCH_*` variable to the worker, and the worker may write the router data folder [R-CODE: `scripts/lib/executable-grade.mjs`]. Only the supervisor process holds the Jev key.
- "No credentials in the sandbox" is not literal for a logged-in CLI. The design separates provider authentication, which the binary needs, from unrelated secrets. The engine never proxies subscription tokens [CODEX]. With broad reads, any key in a file your account can read is readable by a worker that runs as your account. So the Jev key must not sit in an ordinary file of your account. Two storage options fail when a worker runs as the same user as the supervisor:
  - Keychain item. Workers would run as the same user under `(allow default)`. Python's standard library has no Keychain interface, so the supervisor would read the item through `/usr/bin/security`. That tool would then be on the item's trusted list, so a worker could run the same command and may get the key without a prompt.
  - Environment variable set by the supervisor's launcher. A process of the same user may be able to read it, for example with `ps eww <supervisor pid>`, and `(allow default)` does not block that.

  So the key belongs to the supervisor account. No worker runs as that account. The rule is decided (session 2; [Decision 21](../what-we-could-build.md#before-m1-before-a-later-phase-of-m1), option A as amended, 2026-09-27). The key is a separate engine key. It sits in a file with mode 0600, in a mode-700 subfolder of the supervisor's data folder, with no ACL entry for any other account. It is not kept in any Keychain. The full rule is under "Where the engine key sits" in ["OS accounts"](#os-accounts).

  [Added test 14b](milestone-1.md#tests-this-document-adds) is an end-to-end test with a dummy secret (session 2):
  - After a boot with no one logged in as the supervisor account, the supervisor reads the dummy secret.
  - Your daily account, the approval account, the worker account and the worker VMs fail to read it. The worker account tries with and without a sandbox.
  - No evidence export, no file in an exchange folder and no log contains it.
  - The test checks the owner, the mode and the ACL entries of the file and its subfolder.
  - If any read that must fail succeeds, the real key does not go into use until the cause is fixed.
  - The test does not protect against compromised supervisor code or against root.

  The key is not in a Keychain, so the design needs no Keychain deny rule for Claude workers. Such a rule could also have blocked Claude Code's own login if it is kept there (session 2).
- **A separate key is not a separate balance** (session 2; Decision 21). The engine key needs a spending limit that TypeSafe enforces. TypeSafe's public documentation says nothing about limits or balances per key (checked 2026-09-27), and its Master Customer Agreement names no limit per key either (section 2.4). The rule: you check the TypeSafe dashboard before you create the engine key, and if it offers no balance or enforced spending cap per key, the engine key is created in a separate TypeSafe account with its own $5 balance. The supervisor's own counters (the supervisor layer of the Jev cap, [Decision 8](../what-we-could-build.md#before-m2) and [Decision 23](../what-we-could-build.md#before-m1-before-a-later-phase-of-m1)) limit the engine's own use. They cannot limit the use of a stolen key elsewhere. The Jev cap is decided (session 2, 2026-09-27): a provider balance at the smallest amount TypeSafe allows, at most $10 (checked later: $5), with automatic refills (top-up) off, confirmed before the first real call, plus counters in the supervisor. Status 2026-09-27: check 1 found no cap per key, check 2 is confirmed for the current organization (auto-recharge off), and check 3 ("cannot spend more than its balance") stays open until TypeSafe answers in writing. The separate-account rule stays, but under option C ([Decision 21](../what-we-could-build.md#before-m1-before-a-later-phase-of-m1), "the engine key's account") no engine key is created until that answer comes (see "The Jev cap" under ["Budgets and quotas in subscription units"](#budgets-and-quotas-in-subscription-units)).
- The macOS layer uses `sandbox-exec`, a deprecated interface [ACAD, critic warnings]. The router's CI suite checks write confinement and snapshot link refusal, and the live probes checked Codex's own sandbox [R-LOG]. Those probes tested only the shell route, not Codex's `apply_patch` route (session 2). No one tested the boundary against a persistent, adversarial, self-modifying agent: descendant processes and path races over time [ACAD, critic warnings].
- Under `(allow default)`, reads are allowed, so the engine cannot detect a read of a sentinel file (a decoy file that no legitimate process ever touches, so any access to it shows a breach). Detection needs read-denied sentinel paths plus a record of denied access (whether Seatbelt can provide that record is not checked), or a separate account with audited reads.
- Unattended workers with open egress and broad reads can send out any file your account can read, for example after injected text in a target repository. Before unattended runs on real repositories, either use a dedicated OS account with an egress allow-list for provider endpoints, or accept this risk explicitly ([Decision 20](../what-we-could-build.md#decisions-for-the-user)).
- A dedicated OS account or VM might reduce exposure; its login and containment behavior are unverified [CODEX].
- *Session 3, 2026-09-29 (O2):* on the VM path, the host proxy's allow-list limits where traffic goes, not what it carries. An allow-list cannot guarantee that secrets never reach an allowed service. An encrypted relay sees no HTTP host, paths or bodies, so it does no domain-fronting check; V3 records this limitation. See "Network egress on the VM path" under component 4 in ["The eight components"](#the-eight-components).
- Candidate code stays untrusted even when a trusted grader runs it. For learning where the candidate may try to cheat (adversarial learning), the candidate runs in a separate process from the controller that holds the hidden answers [CODEX]. M1 already needs this split, because the router's grader lets candidate code end the grade early and read the grader's files (see component 5).

**What re-grading promises** (session 2; [Decision 13](../what-we-could-build.md#before-m1-before-any-code) follow-up, option B, chosen unanimously). Three promises are kept apart:

- *Rebuild* a candidate. This is promised for every candidate. The patch, applied to the base revision in the source archive, gives exactly the candidate hash. The recorded hidden-test version gives the tests that the candidate was graded with.
- *Re-evaluate* a candidate. An executable re-evaluation is guaranteed only for the maintained evaluation sets: the retention set and the canary set. The canary set is a group of fixed tasks that are re-run after each change or CLI update. For these two sets the supervisor also keeps whatever their grading needs to run on the current pinned runtime. Any other re-run is best effort on the current pinned runtime.
- *Reproduce* an old result. This is never promised.

If a re-run cannot execute, because a dependency, a fixture or an external service is gone, the supervisor records it as "not executable". It never records this as a candidate failure, and never as a reproduced historical result. Learning never uses a "not executable" record as an outcome.

A re-grade record names the candidate hash, the base revision, the hidden-test version, the grader version and the runtime pins it ran on.

It also checks that a bundle with a missing prerequisite is refused at intake, and that a re-run with a missing dependency is labelled "not executable".

### Budgets and quotas in subscription units

Every cost figure in the research is dollars or tokens; none measures plan consumption [ACAD]. The budget therefore works in the units the subscriptions expose. It tracks these separately [CODEX]:
- Claude and Codex window usage, how fresh each number is, and reset times;
- attempts, elapsed time and concurrent jobs;
- Jev spending;
- observed tokens, with missing values marked unknown;
- evaluation and learning spending, apart from useful work.

Rules:
- Reserve capacity before each launch, and keep the reserve line: the share of each window kept free for your own work. A provider-limit failure pauses work; it is not a quality failure [CODEX].
- **Reservations are an internal estimate.** Providers offer no way to reserve capacity, and the cost of one attempt in plan percentages is unknown until M3 measures it. Until then, you set a fixed allowance per attempt, as a percentage of the binding window. A launch goes ahead only if used + reserved + reserve line ≤ 100. After each job, the supervisor compares the estimate with the readings before and after. M3's measured figure later replaces the fixed allowance.
- **Enforceable limits and estimates are different things** [CODEX-REVIEW, finding 13]. Code can enforce the number of model calls, attempts, wall-clock time and concurrent jobs: it refuses the next launch, and at a limit it cancels every job that it launched. Plan percentages are estimates. Providers give no timely usage feed and no maximum for a call that is still running, so a percentage limit only stops the next launch; it cannot stop a call in progress. A hard monetary cap exists only where the provider enforces a spending limit, such as a Codex credit balance of zero (see the credit rule below).
- **An expired unattended authorization stops new unattended launches** (session 2; see "Unattended authorization" under "The task state machine"). When the authorization expires, no new unattended launch starts. A running attempt finishes its current step under the normal limits, and it is not relaunched. The inbox gets one entry that asks you to renew the authorization. Attended runs with their own bounded approval are not affected. The expiry itself moves no task: `ready` tasks stay `ready` (decided 2026-09-30; see "Unattended authorization" under "The task state machine").
- **No new unattended launch on battery power** (session 2; see "Power rules on the MacBook" under "Driver and language"). A new unattended launch needs AC power and a "prevent idle sleep" power assertion. If AC power is lost during an attempt, the attempt continues under its normal limits, and no new unattended launch starts until power returns.
- **A free-disk reserve blocks new attempts** (session 2; [Decision 23](../what-we-could-build.md#before-m1-before-a-later-phase-of-m1), second number, the free-disk rule of Decision 17; option A as amended by Codex, decided 2026-09-27). The rules:
  - It is a reserve, not a plain threshold. An attempt starts only if free space minus that attempt's bounded temporary storage stays at or above 30 GB.
  - The bounded temporary storage covers everything that overlaps during one attempt: the VM's temporary disk, the export, the grading copy and the logs.
  - M1a measures the bound. The bound is the peak storage of a stand-in attempt through export, grading and cleanup. The 30 GB number is revisited then.
  - Until the bound is measured, the rule is advisory. No real run relies on it alone.
  - The check is part of host readiness (see "Host readiness" under ["The task state machine"](#the-task-state-machine)). While it fails, the scheduler claims no task, as during a stop. The inbox gets one entry. The entry clears itself when the check passes again.
  - The measured week before M2 (Decision 17) also records disk use.
  - Context: a laptop disk has limited free space. Raw output is kept 90 days. The source archive and hidden tests are kept for life (see ["Output stores and retention"](#output-stores-and-retention)). macOS needs free space for swap and updates.
  - Rejected: a plain 50 GB threshold (B) and a plain 30 GB threshold (C). A plain threshold checks only at launch. So an attempt admitted just above it could use up the space that macOS needs before cleanup runs. Codex dropped a 15 GB option, because no measurement supports it.

Tests for this decision (session 2, from Codex's conditions). They are part of the M2 exit test in [milestone-1.md](milestone-1.md#what-comes-after). The expiry rules are also in [added test 19](milestone-1.md#tests-this-document-adds) (changed 2026-09-30).
- A missing drift report: the authorization still expires on time.
- A renamed or newly added security file in the router counts as security drift and sends the stop.
- A stale review, recorded for an older router commit range, does not lift the stop.
- An expired authorization prevents unattended launches. `ready` tasks stay `ready`, and exactly one engine-level event and one renewal entry are recorded for the expired period, also after repeated scheduler passes and a supervisor restart (2026-09-30).
- After a valid renewal, `ready` tasks launch under every other check. The renewal moves no `blocked` task. The renewal lifts no stop, resets no launch count and raises no launch limit (2026-09-30).
- A renewal without the high credential and the UV flag is refused.
- A stop request during an active attempt ends the worker.

**Technical traps:**
- **Environment variables that override the login.** In `-p` mode, `ANTHROPIC_API_KEY`, `ANTHROPIC_AUTH_TOKEN` and `CLAUDE_CODE_USE_BEDROCK/VERTEX/FOUNDRY` take priority over the subscription login; the adapter removes them from every child process. A set `CODEX_API_KEY` bills the API [FIT].
- **Settings sources that override the login or add code.** `apiKeyHelper` also takes priority [FIT], but it is a settings entry, so the adapter must control settings sources as well as variables (see "Provider adapters").
- **`--bare`** never uses the subscription login and "will become the default for `-p` in a future release"; pin and test flags on every Claude Code release [FIT].
- **Untrusted repository hooks and MCP servers.** Without `--bare`, `claude -p` runs a project's `.claude/settings.json` hooks and `.mcp.json` servers even in a folder you never trusted [FIT]. So a `claude -p` worker in a target repository would run that repository's code before any grader sees it. The adapter must refuse such repositories or strip those files from the export (*design inference*). Codex reads the repository's `AGENTS.md`, which the Codex adapter treats as untrusted input (see "Provider adapters").
- **Long-lived tokens.** `claude setup-token` makes a one-year token (`CLAUDE_CODE_OAUTH_TOKEN`) for model requests only [FIT]. The engine never holds, passes on or proxies it.
- **Credits and retirements.** Codex keeps running past 100% on bought credits [R-DEC]; GPT-5.5 leaves Codex on 2026-10-14 [FIT].
