**The main points:**
- **A deterministic supervisor.** "Deterministic" means that ordinary code decides every state change and every permission; a model never does. The supervisor starts the real `claude` and `codex` binaries for the model work. It adds no second model loop (a second program in which a model decides the next step). Claude Code already has a planner, subagents, skills and memory files, and it runs on the subscription. This is your position from the session of 2026-09-26.
- **Autonomy first, learning second.** Autonomy needs durable task state: a record of each task that survives a crash. Learning needs an independent verifier: a check the worker cannot change, such as a hidden test suite. The research supports both claims ([H1 and H2](design/research-findings.md#hypotheses-and-verdicts)). No study tested the build order itself, so the order is a design choice (see ["Why autonomy comes first"](#three-kinds-of-memory-and-why-autonomy-comes-first)).
- **TypeSafe Jev in every option.** Jev is a paid classifier model. It answers typed questions about a task, such as its category, how unclear it is, or why an attempt failed. It writes no text or code. It fails safe: when Jev is down or gives a bad answer, the engine takes the fallback that a decision table in code fixes for each job. Jev never grants a permission [FIT], [CODEX].
- **No Deep Agents runtime.** Deep Agents is LangChain's agent framework. Its main loop needs a chat model, and no supported and allowed way exists to run that model on Claude Max [FIT]. LangGraph in Python stays a possible workflow layer for later. From OpenWiki (a tool that keeps a linked wiki of a repository for coding agents), take the ideas, not the tool [FIT].
- **Providers.** Codex will run the unattended work, but only after two of your decisions: the check whether the owner's ChatGPT plan for Codex allows scripted use (Decision 27), and the credit rule (Decision 8). An interactive Claude Code session does planning and clarification. A `claude -p` adapter is built but off by default, because permission for continuous unattended Claude use is unclear. (`claude -p` is Claude Code's headless mode: one scripted run with no interactive screen. An adapter is a small module that starts one provider's CLI and reads its result.) [FIT], [CODEX]
- **Language.** A Python supervisor (your Decision 4, session 2). A small, version-pinned Node bridge, a Node program that runs the router's tested sandbox code and answers the Python code in JSON, is built only if the M1a checks show that the grader must stay on the router's Seatbelt boundary [CODEX].
- **Learning in six tiers ("the ladder"),** ordered from lowest to highest risk. Learning may change what the engine tries, never what it is allowed to do.
- **Unrestricted learning is kept, but paused ("parked").** The idea is not deleted. It starts only when listed conditions are met and you approve. It would then run in a disposable lab: a separate environment that a script can delete and rebuild at any time. The lab holds no real credentials, and that includes any provider login. A proposal leaves the lab only as untrusted material for your inspection. A separate validation stage outside the lab tests it on the real Claude and Codex workers before any adoption (see ["The unrestricted-learning track"](#the-unrestricted-learning-track)).
- **The first milestone (M1)** has a small scope and a large build. The scope: one repository, one task, one writing worker, one independent grader with a small regression suite, at most one retry, and a patch that you review. The build: seven of the eight components, in three phases. M1a first runs feasibility checks for process containment, the approval mechanism and the OS boundary with Codex. M1b then builds an attended loop on a fixture task with one fixed route. M1c adds queue operation and broader routing, then one live run that you watch. The tests use stand-ins: small fake programs that replace `codex` and the Jev API in tests, with no model calls. Under the recommended plan, M1 has three real `codex exec` runs, plus the short real runs of check V6 in M1a (session 2). The fixture run may use two attempts, so it may hold two `codex exec` calls (session 2, Decision 23). The M1a runs follow the operating budget of Decision 23 (session 2). The fixture run's limit is decided (session 2, Decision 23): the M1a budget for each attempt, and at most one retry. The live run gets a usage limit that you set first. Trying Path B first, or changing the Codex configuration after the probe run, adds a real run. M2 to M5 come after M1 (see ["The first milestone"](#the-first-milestone-m1)).

## What the research says

The full findings, with every number and source id, are in [design/research-findings.md](design/research-findings.md). Most sources are 2025-2026 preprints, often run by the method authors on one benchmark [ACAD]. These seven findings shape the design most:

1. **Learning depends on the outcome check.** With a trusted signal, learning without weight changes gave moderate gains. ReasoningBank gained 4.6 and 3.4 points on SWE-bench Verified, a benchmark of coding tasks graded by tests [reasoningbank-2025]. The method authors report these gains, and [ACAD] found no independent replication. Without a trusted signal, results stopped improving or got worse. Under one protocol, skills that models wrote before solving scored 8.1 to 11.5 points below no skills [skillsbench-2026]. An LLM that kept rewriting its memory store made it worse over time, even from ground-truth inputs [faulty-consolidation-2026].
2. **Memory helps in narrow cases, and simple storage is enough there.** When later tasks depend on earlier facts, no memory passed 21/180 tasks, a plain verbatim log 82/180, and a typed-plus-raw pipeline 83/180 [dreambench-swe-2026] (*preprint, single author, single source*). Revising outdated facts is the weakest capability: every method scored at most 28% on multi-hop fact updates, where the answer depends on a chain of facts [memoryagentbench-2025].
3. **"Tests pass" is useful, but it is not proof.** 29.6% of test-passing patches behave differently from the reference [patchdiff-2025]. Reward hacking means passing the check without doing the intended work. GPT-5 did it on 54% of impossible SWE-bench tasks. A "flag for human" exit cut this to 9%, with much less effect for Claude Opus 4.1 [impossiblebench-2025]. Answers can leak through readable history: Claude read git history that earlier trials left [anthropic-evals-2026] (*vendor*).
4. **Long autonomous work mostly fails, and resuming is not safe.** The best setup resolved 25% of 112 dependency-structured tasks [loopsbench-2026]. When k processes resumed one paused LangGraph run at the same time, the approved action ran k times, in 36 of 40 test configurations [resume-means-resume-2026] (*preprint, single author*).
5. **Self-modifying agents gained, hacked and cost a lot.** DGM (the Darwin Gödel Machine, a coding agent that changes its own code) rose from 20.0% to 50.0% on a SWE-bench Verified subset, in author-run, mostly single runs. Runs cost about USD 7,000 to 22,000 [dgm-2025], [sica-2025]. Gains shrank outside the training tasks: up to 14.1 points, against up to 4.7 [rrsi-2026]. In a DGM side experiment, one variant got a perfect score by removing cheat-detection markers from code it could edit [dgm-2025]. [ACAD] read this through a summary of a blog page.
6. **Learned text is a way in for attackers, and enforced controls beat requests.** Skill extraction dropped safety detection from 98.5% to 11.4% [skilljack-2026]. In a red-team test (a test in which people attack on purpose), a phishing message (a fake message that tries to steal data) made Claude send credentials to an outside server in 24 of 25 tries. Hard limits came from sandboxes, egress limits (limits on outgoing network traffic) and graders the agent cannot reach [anthropic-containment-2026] (*vendor*).
7. **Keep-or-revert decisions are noisy.** The rule "keep a change if the score went up" accepted 30-42% wrong edits [pace-2026]. An unchanged model showed fake "learnings": in 5.8% of comparisons it seemed to beat itself (a false-win rate of 0.058) [phantom-gains-2026].

The seven hypotheses and their verdicts are in [research-findings.md](design/research-findings.md#hypotheses-and-verdicts). This document relies most on H1 (autonomy needs durable state), H2 (learning needs an independent verifier) and H4 (learned routing numbers: lowest risk, lowest value).

## Three kinds of memory, and why autonomy comes first

The router research of 2026-09-25 already proposed keeping three kinds of memory apart [R-0925]. This design uses the same split.

| Kind | What it holds | Who writes it | Authority | What may change it |
|---|---|---|---|---|
| Instructions | `CLAUDE.md`, `AGENTS.md`, rules, human-written skills | You | Rules the model reads | Only you; learning may propose, never write |
| Task state | Tasks, attempts, effects, approvals, evidence, the current snapshot | The supervisor, from observed facts | The truth about the current work | Only the state machine, in transactions |
| Experience | Lessons and records reused across tasks | Learning channels, from verified outcomes | Lowest trust: a hint, never a rule | The ladder's gates, with provenance (a record of which run and commit produced the item) and rollback |

**Instructions.** Claude Code loads its memory files as context, not as enforced configuration [ACAD, citing the Claude Code memory docs]. Auto memory loads the first 200 lines or 25 KB per session [PLAT]. Static context files did not change correctness in one study [context-files-ablation-2026]. The studies disagree about their effect on efficiency: one found 28.64% lower runtime [agentsmd-efficiency-2026], and another found more than 20% higher inference cost [R-0925], [ACAD]. So instructions stay short and human-owned. They carry rules, not facts the engine can observe itself.

**Task state.** H1 is supported with one caveat. Durable external state is how long-horizon harnesses are built, and external verified state gave the largest reported harness gains, mostly on computer-use tasks [loopsbench-2026], [longhorizon-harness-2026]. (A harness is the loop, prompts and tools around a model.) No ablation (a test that removes one part to measure what it adds) isolates the state component, and resume layers are unsafe without explicit design [resume-means-resume-2026]. The caveat belongs here: when later tasks depend on earlier facts, a plain verbatim log was enough [dreambench-swe-2026]. So the design keeps a sanitized, append-only journal per task as part of task state: secrets are removed, and entries are only added, never changed. A model never rewrites it.

**Experience.** Gains exist with a trusted signal [reasoningbank-2025], [ace-2025]. Self-written skills hurt under one protocol [skillsbench-2026], self-written lessons did not help [tf-grpo-2025], consolidation (an LLM rewriting the memory store) decays [faulty-consolidation-2026], experience is an injection path (a way to plant instructions) [skilljack-2026], and retirement (removing outdated records) is the weakest area [ACAD]. Experience therefore gets the lowest trust and the strictest gates.

**Why autonomy comes first.** The whole list is *design inference*; no study tested the build order.
- Autonomy needs task state, not experience (H1).
- Learning needs verified outcomes (H2): outcomes that an independent grader checked.
- So learning depends mainly on the verifier, not on autonomy. The autonomous loop is one source of verified outcomes. An offline evaluation over fixed tasks is another, and it needs no autonomy.
- **A departure from [R-0925].** The router research put executable outcome evaluation first and resumable task records third ("Recommended order") [R-0925]. This document starts with the autonomous loop in M1 and M2, the first two milestones (all five are in ["The first milestone"](#the-first-milestone-m1)). The third milestone, M3, is the evaluation harness: the code that runs fixed tasks and measures the results. The reason for the order: in claude-domore the evaluation harness is built and tested with stand-ins, so it does not need to come first. Its code, fixed task sets and report format are built next to M1 and M2. M3 then runs it with the real workers: fixed baselines, A/A runs (the unchanged engine run against itself, to measure noise) and the measurements. M1 already has the independent grader, so the loop produces verified outcomes from the start. This order is a design choice, not a research result.
- So autonomy first is a project choice, not a necessary dependency: learning could also start from an offline evaluation, with no autonomy [CODEX-REVIEW, finding 2]. What must be avoided in any order is learning from unverified outcomes. That is the failure case in [skillsbench-2026] and [tf-grpo-2025]: self-written content without verified evidence. [faulty-consolidation-2026] adds a separate warning: when an LLM rewrites the store, it decays even from ground-truth inputs.
- A weak reverse dependency exists. Learned routing numbers could make autonomy cheaper, but their reported value is low (H4), so they can wait.

- Which subscription does the coding?

## Recommended architecture

The full design is in [design/architecture.md](design/architecture.md). The principle: ordinary code owns state transitions and permissions; models propose work and produce artifacts [CODEX]. Most details are *design inference*.

**Driver and language.** The driver is the deterministic supervisor. An interactive Claude Code session is the planning front-end. It drafts specifications and clarification answers, but it owns no state and approves nothing. The language is your choice (Decision 4). One choice is a Python supervisor with standard-library SQLite and a small, pinned Node bridge to the router's sandbox code. The other is one newer Node runtime, whose built-in SQLite is still a release candidate [FIT], [CODEX].

**The eight components** [CODEX]: (1) task admission and clarification; (2) durable state and scheduler; (3) provider adapters; (4) workspace and process supervisor; (5) independent verification; (6) budget and quota control; (7) human approval inbox; (8) learning experiments and artifact registry. Engine state, such as the database, approvals, evidence, quota readings and hidden checks, lives outside every worker's write set (the paths a worker may write). Approvals come only through a human-only channel that the model cannot reach (Decision 26). That channel needs an approval identity or a signing key that neither the workers nor the planning session hold. A terminal prompt is not enough, because software can create a pseudo-terminal (a software pair of endpoints that looks like a terminal) and type into it [CODEX-REVIEW, finding 3].

**OS accounts.** These guarantees need separate OS accounts. The supervisor runs under its own account, which owns the database, the raw attempt output and the engine's own Jev key. The key is a mode-0600 file in a secret subfolder of the supervisor's data folder (Decision 21, session 2). The Codex worker runs under a dedicated worker account. Approvals come from a separate approval account or a hardware key. The planning session runs under your daily account, which can neither write engine state nor read raw output. That account must not be able to become root (the system administrator user, which can act as any account). An admin account can usually become root through `sudo` (a program that runs a command as another user) with its own password. Everything that the supervisor and worker accounts run (the Python and Node runtimes, Codex, the supervisor's own code and its launcher) sits in one folder outside every home folder, which root owns and none of these accounts can change. Copies of Python, Node and Codex that belong to the daily account do not qualify, so the admin account installs new copies. *(Session 3, 2026-09-29: the admin account installs Python and `container` first. A host Codex and host Node are installed only when their trigger occurs; see Decision 5, "the runtime folder".)* Your daily account can still stop the engine at any time through a stop request on the input socket (Decision 26, part 26d). Only you restart it, through the human-only channel (see ["OS accounts"](design/architecture.md#os-accounts); Decisions 26 and 31).

**Task states** [CODEX]: `proposed`, `needs_clarification`, `ready`, `running`, `checking`, `verified_candidate`, `awaiting_approval` and `accepted`, plus `retryable`, `blocked`, `cancelled` and `effect_unknown`. Code checks the conditions for every move.

**Side effects.** A side effect changes the world outside the supervisor's database: a model launch, a commit, a push or a PR. The supervisor records the intent and a stable operation id before the effect, then records the result [CODEX]. On resume, it reconciles with observed reality (git HEAD, snapshot hash, lock ownership, provider limits) instead of repeating the last instruction. An uncertain launch goes to `effect_unknown` and is never relaunched automatically. Each claim of a task gets a fencing token, an increasing ownership number; a result with an older token is rejected.

**What containment covers and does not cover.**
- Covered: the router's OS boundary lets the worker write only its workspace, the router data folder and a private temporary folder. The worker cannot read the verification root (the folder with grader copies and the evidence of all trials). The grader has no network and no inherited credentials [R-README].
- Not covered: credentials. Worker network and broad host reads stay open.
- Not covered: other copies of a past failure's fix. So llm-orchestrator tasks need a separate OS account or VM (Decision 16).
- Not tested: a persistent, adversarial, self-modifying agent, and Codex inside the boundary. A spike (a short throwaway build that tests one question) first runs stand-in steps. You then choose Path A (Codex's own sandbox) or Path B (an outer boundary), and one real run tests the chosen configuration; see Decision 25. *(Session 2: M1a now tries the VM path first. There, Decision 25's rule applies to every worker CLI: its own sandbox stays on in full mode, and a probe matrix tests every write route. Paths A and B apply to the worker-account fallback.)*
- Not covered by the router's method: descendants that leave the worker's process group by starting their own session. M1 chooses a mechanism that holds every descendant: a dedicated worker OS account used by one attempt or one grading at a time. Codex then keeps its login and session files in that account. After each attempt the supervisor copies the session files into its own store, and a launcher program deletes the originals. When it cannot show that all processes ended, it quarantines the workspace: the workspace is kept apart, never reused, and not graded while that doubt remains [CODEX-REVIEW, finding 6].
- Not proved by the router's grader: which checks ran. Its status is `passed` on exit code 0 within its time and output limits, and candidate code that it runs can end the grade early or read the grader's files. M1 splits grading into a protected checking process and a separately confined candidate process, and it records every completed check [CODEX-REVIEW, finding 4].

**Budgets in subscription units.** No research figure measures plan consumption. So the budget tracks these separately: window percentages (the used share of each provider usage window, such as Claude's 5-hour and 7-day limits), attempts, time, Jev spending and learning spending. A launch goes ahead only if used + reserved + reserve line ≤ 100. The reserve line is the share of each window kept free for your own work. Unknown quota blocks an unattended launch. Code can enforce limits on calls, attempts and time, and it cancels every job it launched at a limit. Plan percentages stay estimates, so a hard monetary cap exists only where the provider enforces a spending limit [CODEX-REVIEW, finding 13].

**Provider adapters.** Codex runs unattended work through `codex exec` with the saved ChatGPT login, on private repositories only, and only after Decisions 8 and 27. An interactive Claude Code session does planning and clarification. A `claude -p` adapter is optional and off by default (Decision 6).

**Reuse.** Each router file is copied (a pinned copy with its tests), called (its command run from a pinned copy), ported to Python, or used only for its lessons or patterns, as named in the [reuse table](design/architecture.md#what-we-reuse-from-the-router).

## TypeSafe Jev in claude-domore

The full design is in [design/jev.md](design/jev.md). Jev is in every option; the options table shows where it sits in each one. In the unrestricted lab, the lab controller calls Jev with a separate key.

**The first three jobs to build** [CODEX]:
1. **Job 1, triage.** The task category feeds the baseline routing table, which chooses only among routes that code allows.
2. **Job 5 plus `self_contained`, ambiguity.** A low threshold sends a task to `needs_clarification`. A missing signal never moves a task forward.
3. **Job 3, failure triage.** It suggests the next move after a failed check. Code enforces the retry cap. A "usage limit" or "environment" class pauses the task instead of spending a retry. Only provider evidence, such as Codex's own usage-limit event, marks a pause as a provider limit that ends by itself after a reset. A Jev "usage limit" class without that evidence gives a pause that only you can end.

**The other jobs** [FIT]: reading a worker's claim (2), stop or continue (4), memory retrieval (6), lesson intake (7), claim re-check after code changes (8), skill or workflow choice (9), duplicate records (10), and a signal where no executable check exists (11).

**Rules for every call:**
- **Pin the version:** `jev-1.13.0`, not `jev-latest` [FIT].
- **Fail safe, not fail open.** When Jev fails, the router runs the call as written [R-DEC]. The engine instead takes the fallback that the [decision table](design/jev.md#decision-table-jev-answers-and-failures) fixes for each job and each kind of failure: the default route, no step past a human approval, and a visible inbox or log entry. Permissions never depend on Jev; route selection, retry and cost are separate rows of that table [CODEX-REVIEW, finding 8].
- **Minimal data.** Send only the fields each question needs, with secrets stripped and excerpts redacted as a best effort. Only allow-listed repositories send data. The key never reaches a worker, the bridge or a log.

**Calibration against matching labels.** Calibration means checking that "0.8" comes true about 80% of the time on your own tasks. Each question is calibrated against its matching label, not against task success [CODEX]. For example, the ambiguity signal is checked against whether clarification was really needed, judged on audited samples of both escalated and non-escalated tasks, not only on your answers to escalations [CODEX-REVIEW, finding 10]. A reliability table (predicted probabilities against observed rates) and a Brier score (the mean squared difference between probability and the real 0/1 outcome) are measured per question and per version. Thresholds come from that data [FIT].

**Jev must never decide** anything that grants a permission or states a fact that code can check: permissions, lock ownership, remaining quota, the truth of a test pass, approval validity or promotion (making a tested learned change the new default) [CODEX]. The limits for each job are in [jev.md](design/jev.md#jobs-for-jev). Jev is a signal, never a permission. Injected text can move its answer, so Jev alone may move the engine only toward caution [FIT].

## Self-learning: the ladder

The full design is in [design/self-learning.md](design/self-learning.md). The rule: learning may change what the engine tries, never what it is allowed to do. No learned artifact touches sandbox modes, permissions, locks, budgets or the definition of success [FIT]. Every tier needs versioned artifacts, source evidence, rollback, a budget and a baseline without the adaptation [CODEX].

| Tier | Channel | Entry condition |
|---|---|---|
| 0 | Observe only | M1 passed: reliable state and verification |
| 1 | Routing numbers and escalation thresholds | Repeated eligible task categories, trustworthy outcomes, logged selection probabilities |
| 2 | Experience retrieval | Related tasks exist; records have provenance |
| 3 | Prompts, skills, tool descriptions | A specific repeated problem; enough evaluation budget |
| 4 | Workflows, harness components | Stable lower-level execution; a measurable bottleneck |
| 5 | Engine code | Proven recovery, protected evaluation, a separate experimental environment |

Tier 0 records outcomes and adapts nothing. Changes at Tiers 4 and 5 reach the engine's core (components 1 to 7) only through a release you approve. Jev is never an acceptance input at any tier.

**A default order, not a strict one.** The tiers show rising risk, not a queue. A narrowly useful experience record may be worth testing before a learned router, and each channel needs its own evidence [CODEX]. What is strict is each tier's own entry condition.

**Paired comparisons.** The current version (the incumbent) and the candidate run on the same tasks, with error ranges per task family. Before running, you set the minimum useful improvement, the acceptable regression and the maximum experiment budget. An A/A run comes first, to measure how often noise looks like a win (0.058 in one audit [phantom-gains-2026]). "Inconclusive" is a valid result: if the budget cannot separate the candidates, nothing is promoted [CODEX].

**Stop criteria** [CODEX]. A channel is disabled at once on unauthorized access, tampering, secret exposure, a failed rollback, workers that cannot be stopped, or a failure of the safety suite or the retention set (fixed tasks re-run after each change to catch lost abilities). Promotions stop on model drift (a provider's model starting to behave differently), stale evidence, exhausted budgets or inconclusive results. The full list is in [self-learning.md](design/self-learning.md#stop-criteria).

## The unrestricted-learning track

The complete record of the idea is in [design/unrestricted-learning.md](design/unrestricted-learning.md). You required it to be captured in full (your session decision S2).

**What "unrestricted" means.** The engine may change anything about itself from its own outcomes: routing, memory, prompts, skills, workflows and its own code, with no fixed list [ACAD]. The closest published systems, Hyperagents and Ouroboros, are not truly unrestricted [ACAD].

**Why a protected core and unrestricted learning are different designs.** Learning needs a measurement of whether a change helped. A learner that can change the measurement can "improve" by changing it. In several studies, an agent that could reach its grader did so [dgm-2025], [aide2-2026], [metr-reward-hacking-2025]. So the evaluator, its data, the budget and the stop switch must stay out of the learner's reach, and that part is restricted by definition [CODEX]. The lab is unrestricted inside, with the measurement and the lab boundary outside. The variant with no fixed limits is recorded but not built: its gains could not be measured (Decision 11).

**The decision.** A parked research track in a disposable lab: kept, not deleted. It opens only when the preconditions are met and you approve. It has no automatic promotion [CODEX]. It holds no production credentials, and that includes any provider login [CODEX]. The learner and candidate processes hold no credentials at all. Only the protected lab controller holds a credential: its own separate Jev key, outside the learner's boundary (session 2; Decision 22). The lab uses a local model. Decision 22 allows a free local model for the lab only, and a gain on that weaker model is never evidence by itself (session 2). A proposal leaves the lab only as untrusted material for your inspection. A separate, controlled validation stage outside the lab tests it on the real Claude and Codex workers before any adoption; only that stage holds a provider login. An earlier version allowed one provider login inside the lab; after the second Codex review this design follows Codex instead (Decision 29) [CODEX-REVIEW, finding 14].

**Where the details are.** unrestricted-learning.md holds the lab charter (Decision 10, 2026-09-30), the 15 needs, the protected core, the 11 preconditions, the lab design, the known failure modes, the guards in published systems, the kill criteria and the open problems. In short: the lab stops a run at once on any sign that its boundary failed. It accepts a candidate only under an evaluation plan fixed before the lab opens: the comparison method, the minimum useful effect, the regression tolerance, a budget of hidden-set queries and an untouched final set [CODEX-REVIEW, finding 15]. It closes the track if no gain on the hidden tasks meets that plan within its budget.

A guest with no network device removes direct paths, but it does not prove the relay safe. The item is not mandatory if the current internal-network design passes V3.
            - *Later, at the evidence-log design:* OCSF event classes (a standard JSON format for security events). V3 already needs structured denial records now: the attempt id, the policy hash, the reason and the positive-control results, with no raw credentials or request bodies.
        - *Before V3 acceptance (Codex, blocking clarification):* the encrypted relay does not terminate TLS, so subscription tokens stay out of the host proxy. For the same reason the relay cannot see the HTTP Host or `:authority`, paths or bodies. SNI (the host name in the TLS handshake) is not the HTTP authority. So V3 needs precise pass criteria for the encrypted-relay design, tests of the required provider endpoints, and a recorded limitation: no domain-fronting check (the relay cannot detect a request that shows an allowed name in SNI but asks for another service inside the encrypted traffic). Decrypting subscription traffic is never the solution. An allow-list cannot guarantee that secrets never reach an allowed service.
        - *Team view:* for O1, Claude chose D, Codex chose D as amended, and Jev chose D at 0.94. For O2, Claude chose to adopt, Codex chose to adopt with the conditions above, and Jev chose A (add them as design notes now) at 0.98. Claude, Codex and Jev agree that script 03 does not change. Record: in the private working repository (Codex answer, mapping and critic notes).
- **24. How is the first quota reading after a reset obtained?** Recommendation: first, the supervisor reads `rate_limits` from the newest Codex session file of any thread that its account can read, and trusts it only inside its window. It can read its own copies from earlier attempts, and your own `~/.codex/sessions` only if you give the supervisor account read access to that folder, through ACL entries, because the setup step in Decision 26 closes your home folder. If no such reading exists, the task stays `blocked` with `quota_unknown`, and you start an attended first launch with an allowance you announce. This keeps the queue unattended whenever a real reading exists, and it never launches on a guess (["Budgets and quotas"](design/architecture.md#budgets-and-quotas-in-subscription-units)).
    - **Changed by Decision 26b (session 2 review):** on the VM path, the session files live on the credential volume inside the guest, so the supervisor has no ACL read path to them. The quota source then becomes the V7 reader VM: a short-lived VM that runs `codex app-server`, where the supervisor may call only `account/rateLimits/read` and never `ConsumeAccountRateLimitResetCredit`. Session files become the fallback. Under the worker-account fallback, the text above applies.
- **27. May unattended Codex runs start before the owner's ChatGPT plan is checked?** Recommendation: no. Before M2, check OpenAI's plan table for that plan and keep a record of the answer. Until then, Codex runs are attended only. This mirrors Decision 6 for `claude -p` ([FIT], "OpenAI policy findings").
- **32. How should human friction be reduced after M1?** (added 2026-09-30, from the security-vs-autonomy consult). From M2, the work inside an approved task runs without you. The costs are at the edges: a successful task needs two high-impact signatures, each with a switch to the approval account and a read of the patch, and most listed block reasons need your unblock. No one has measured which cost dominates. Options:
    - **A. Keep the gates, and measure.** At M2, go beyond the planned count of approvals per role (see "Review at M2" under "Human-only actions" in [architecture.md](design/architecture.md#the-eight-components)). Also record the minutes you spend per accepted task, account switches, interruptions by reason, waiting time, and tasks finished without your action.
    - **B. The PR is the delivery.** An approved task ends at a pushed task branch and a draft PR, with no signature per patch; your merge becomes the acceptance. Cost: it moves push and PR from M5 (Decision 7) to M2. The engine then needs write access to the git host, and a push can trigger repository automation. The guarantee holds only if the planning session cannot merge, so the merge needs its own human-only route.
    - **C. Batch approval.** One high-impact signature approves a fixed list of task specifications, each with its own limits, plus a total budget. A queue that can gain tasks later is broader authority and is not part of this option.
    - **D. Automatic recovery for narrow transient failures.** Extend the rule that quota and host-readiness blocks already use: a block with a narrowly defined transient reason returns by itself after a fresh check, within the existing budgets and launch limits. Uncertain effects, security blocks and scope changes stay with you. Each new reason is added only when M2's measurements show it happens.

    Recommendation: A at M2, and D as the first lever to try, one measured reason at a time. B and C stay later proposals. Team view: Claude A (then D). Codex A with the wider metrics; it rated B's git-host and merge conditions as blocking and proposed D. Jev B 0.38, C 0.35, A 0.27 at confidence 0.07 (no real lean); `option_missing` 0.42.
